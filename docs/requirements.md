# MultiProvider LLM Toolbox 需求说明

## 1. 项目背景

MultiProvider LLM Toolbox 是一个从零设计的网页版大模型接口调用工具箱。它面向需要在一个界面中切换多个大模型 Provider、进行文本对话并观察流式输出的开发者和内部使用者。

项目必须支持四个 Provider：OpenAI、Anthropic 为核心必需 Provider，DeepSeek、GLM 为本项目必须实现的扩展 Provider。四者都必须有完整 Adapter 和模拟契约测试；若真实 API 条件不足，至少交付完整 Adapter、固定夹具和 mock 上游测试。

阶段一只完成需求、架构、接口契约、安全设计、验收标准和参考研究文档，不开始业务编码。

## 技术栈定稿

采用 Next.js + React + TypeScript，使用 Next.js Route Handler 作为统一 API 层，浏览器端负责页面、会话状态和本地数据。该选择适合单仓库 Web 应用、SSE 流式响应和 Docker 部署。

## 2. 用户角色

### 2.1 普通使用者

- 在网页中选择 Provider 和模型。
- 输入文本消息并查看非流式或流式回答。
- 使用基础提示词模板。
- 看到可理解且不泄露密钥的错误提示。

### 2.2 运维/部署人员

- 通过服务端环境变量配置 API Key 与 Provider 地址白名单。
- 使用 Docker 启动服务并检查健康状态。
- 查看不包含敏感信息的运行日志。

### 2.3 开发与测试人员

- 根据统一 LLMProvider 接口新增或替换 Provider 适配器。
- 运行自动化测试与 CI 检查。
- 验证安全边界、超时、错误和流式协议。

## 3. 用户故事

1. 作为普通使用者，我希望选择 OpenAI 和具体模型，发送一段文本并获得回答。
2. 作为普通使用者，我希望切换到 Anthropic、DeepSeek 或 GLM，而无需理解各厂商请求格式。
3. 作为普通使用者，我希望选择流式输出，及时看到回答生成过程。
4. 作为普通使用者，我希望网络错误、上游 4xx/5xx 和参数错误被统一展示。
5. 作为普通使用者，我希望使用预置提示词模板快速开始对话。
6. 作为运维人员，我希望真实 API Key 只存在服务端环境变量中，而不会进入浏览器、日志或 URL。
7. 作为运维人员，我希望只能调用已配置的 Provider 地址，避免 SSRF 和任意代理。
8. 作为开发人员，我希望通过统一接口测试 Provider，而不必在业务层编写厂商分支。
9. 作为开发人员，我希望 Docker、测试和 CI 的验收条件清晰可执行。

## 4. 功能需求

### 4.1 网页聊天

- 提供消息列表、输入框、发送/停止操作和响应状态。
- 明确区分用户消息、助手消息和系统提示。
- 支持文本对话；阶段一不包含图片、语音或文件输入。
- 支持多轮上下文；当前会话最多保留 50 条消息。
- 支持最多 5 个本地会话，刷新页面后可恢复；聊天记录只保存在浏览器。
- 助手回答支持基本 Markdown 展示；不执行未经信任的 HTML/脚本。
- 支持生成中的停止和失败后的重试；停止后保留已收到的文本并标记为已停止。
- 暴露 temperature 与 max_tokens 两个基础参数，其他厂商参数不纳入 MVP。
### 4.2 Provider 与模型

- 页面展示服务端返回的 Provider 列表及可用模型。
- 用户只能从服务端声明的 Provider 和模型中选择。
- 核心必需 Provider：OpenAI、Anthropic。
- 必须实现的扩展 Provider：DeepSeek、GLM；扩展不等于可选，四者均须通过模拟契约测试。
- 浏览器不得提交任意 `baseUrl`；Provider 地址由服务端白名单配置。

### 4.3 对话模式

- 支持非流式响应：一次返回完整助手消息。
- 支持流式响应：服务端以定义好的事件格式持续发送增量内容、完成和错误事件。
- 消息顺序、角色、空消息和最大消息数量必须经过服务端校验。

### 4.4 提示词模板

- GET /api/prompts 返回服务端内置只读模板。
- 用户自定义模板在浏览器 LocalStorage/IndexedDB 中创建、编辑和删除，不进入服务端 API。
- 模板内容仅作为普通文本插入输入框；必须限制名称和内容长度，不执行模板中的 HTML/脚本。
- 不在模板中保存 API Key、访问码、密码或内部敏感信息。
### 4.5 统一 Provider 接口

- 定义 `LLMProvider`，至少包含 Provider 标识、模型目录能力、非流式调用和流式调用。
- 优先使用 `OpenAICompatibleAdapter` 支持 OpenAI、DeepSeek、GLM，并为四个 Provider 分别维护地址、密钥变量、模型目录和 mock 契约夹具。
- `AnthropicAdapter` 独立处理 Anthropic 的消息、鉴权和流式事件语义。
- 若 GLM 在鉴权、请求字段、响应结构或流式事件任一关键方面无法通过兼容适配器稳定映射，则拆分为 `GLMAdapter`，不改变业务层契约。

### 4.6 运行与交付

- 服务端从环境变量读取 API Key。
- 提供 `/healthz` 健康检查。
- 提供 Docker 部署方案。
- 提供单元、契约、集成（可使用模拟上游）测试策略与 CI 门禁。
- 后续阶段补充安全测试、amd64 镜像及公开部署访问控制。

## 5. 非功能需求

- 安全：真实 API Key 不进入浏览器、日志、异常、响应、URL、测试快照或 Git。
- 可维护性：业务层不得直接依赖厂商 SDK 细节；Provider 通过适配器隔离。
- 可靠性：上游请求必须有超时、取消和 4xx/5xx 归一化处理。
- 可观测性：记录请求耗时、Provider、模型和结果类别，但不得记录密钥与完整敏感内容。
- 可测试性：核心契约可使用固定夹具和模拟上游验证。
- 可部署性：支持 Docker，配置通过环境变量注入。
- 性能：流式首字节延迟和完整响应耗时可测量；具体 SLO 在阶段二确定。
- 兼容性：桌面和移动端主流现代浏览器可使用；不承诺旧版浏览器。

## 6. 安全需求

1. API Key 只能从服务端环境变量读取，禁止前端输入、持久化或回显。
2. Provider 地址只允许服务端白名单值，拒绝任意 `baseUrl`。
3. 默认不开放任意来源 CORS；仅允许明确配置的前端来源。
4. 限制请求体、消息数量、单条消息长度、总字符数和 `max_tokens`。
5. 校验消息角色，只允许 `system`、`user`、`assistant`，并按产品策略限制 system 消息来源。
6. 上游连接必须设置连接、读取和总时限；正确处理取消。
7. 统一错误响应不得包含 API Key、Authorization、上游原始敏感头或内部堆栈。
8. 设计限流、审计和 SSRF 防护；详见 `security-design.md`。
9. 默认按本地部署设计；若公开部署，必须启用服务端 `ACCESS_CODE` 简单访问码。阶段一不实现用户注册、登录、多租户或企业权限。

## 7. 不做范围

- 用户注册与登录。
- 多租户、计费、企业权限系统。
- MCP、插件市场、复杂 Agent 编排。
- 图片生成、语音、桌面端、云端聊天同步。
- 任意自定义 API URL。
- 本阶段不交付业务代码、安装依赖或下载外部文件。

## 8. 约束和假设

- 项目名称暂定为 MultiProvider LLM Toolbox。
- OpenAI、Anthropic 为核心必需项；DeepSeek、GLM 为必须实现的扩展项。四个 Provider 都必须有 Adapter 和模拟契约测试；真实 API 不可用时不得阻塞 mock 交付。
- 默认本地部署；公开部署时由运维显式设置 `ACCESS_CODE`，不引入用户注册、多租户或账号隔离。
- API Key 由部署环境负责注入和轮换，应用不提供密钥管理后台。
- Provider 模型目录可采用静态配置或服务端配置文件，不要求实时从厂商拉取。
- 默认以单服务实例、无账号上下文为阶段一设计边界；聊天记录和自定义提示词使用浏览器本地存储，服务端不承诺跨用户共享或云端持久化。
- 上游厂商接口版本、模型可用性和地区网络条件可能变化，适配器必须可配置且有契约测试。
